# Git 작업 흐름

사용자 요청과 프로젝트별 명시적 규칙을 우선하고, 별도 규칙이 없으면 이 기본값을 적용합니다.

## 브랜치 이름

`{type}/{short-description}`을 기본으로 사용합니다. 실제 티켓이 있으면 `{type}/{ticket}-{short-description}`으로 작성할 수 있습니다. 설명은 짧은 영문 소문자와 하이픈으로 쓰고 티켓 번호는 원본을 유지합니다.

| 접두사 | 용도 | 예시 |
|---|---|---|
| `feature/` | 새 기능 | `feature/message-search` |
| `bugfix/` | 버그 수정 | `bugfix/token-refresh` |
| `hotfix/` | 운영 긴급 수정 | `hotfix/login-failure` |
| `refactor/` | 동작을 유지하는 구조 변경 | `refactor/backend-router` |
| `docs/` | 문서 변경 | `docs/readme-architecture` |
| `test/` | 테스트 변경 | `test/message-pagination` |
| `chore/` | 도구·설정·의존성 관리 | `chore/update-dependencies` |

프로젝트가 `feat/`·`fix/` 같은 다른 접두사를 명시했다면 그 규칙을 따릅니다. 도구 이름을 이유로 기본 접두사를 작업 종류와 관계없이 붙이지 않습니다. 사용자가 정확한 이름을 지정하면 그대로 사용합니다.

## 작업 순서

1. Git 상태·현재 브랜치·원격·기준 브랜치를 확인하고 기존 미커밋 변경을 보존합니다.
2. 기본 브랜치 또는 사용자가 지정한 기준에서 작업 브랜치를 만듭니다. `develop` 같은 중간 브랜치를 임의로 가정하지 않습니다.
3. 목적이 같은 변경을 묶고 변경에 맞는 검증을 수행합니다.
4. 승인된 범위에서 커밋·푸시하고 로컬 커밋과 원격 반영을 확인합니다.
5. 실제 최종 변경을 설명하는 PR을 만들고 리뷰 피드백을 반영합니다.
6. 머지와 브랜치 삭제는 요청된 범위에서만 수행합니다.

커밋·푸시·PR 생성 권한을 이미 받은 작업은 반복 확인하지 않습니다. 구현·문서 수정만 요청받았거나 명시적으로 로컬 작업으로 제한된 경우에는 원격 게시 권한까지 추정하지 않습니다. PR 생성은 머지 승인과 별개입니다.

커밋 형식은 [커밋 지침](commit-messages.md), 제목·본문은 [PR 지침](pull-requests.md)을 따릅니다. 머지 전략·브랜치 보호·필수 리뷰 수는 프로젝트 설정을 따르며 이 지침만으로 강제하지 않습니다.
