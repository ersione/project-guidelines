# Pull Request 작성

리뷰어가 대화를 읽지 않아도 문제, 최종 동작, 검증 근거를 판단할 수 있게 작성합니다.

## 제목

- 실제 티켓이 있으면 `[TICKET-ID] 변경 요약`을 사용할 수 있습니다.
- 티켓이 없으면 `type(scope): 변경 요약` 형식을 기본으로 합니다. `scope`는 생략할 수 있습니다.
- 최종 구현 범위로 제목을 갱신하고 이슈 번호나 기능을 지어내지 않습니다.
- 한국어로 읽기 쉽게 쓰되 프로젝트가 지정한 언어·형식을 우선합니다.

```text
docs: README에 아키텍처와 설치 흐름 추가
```

## 본문

구체적인 문제와 결과를 먼저 설명합니다. 필요하면 발생 조건과 변경 전후 예시를 붙입니다. 작은 PR은 한두 문장과 검증 결과로 충분합니다.

규모에 따라 다음 내용을 선택합니다.

- 문제·목적과 사용자에게 보이는 결과
- 리뷰에 필요한 주요 변경·설계 판단
- 실제 실행한 테스트·명령·수동 확인과 결과
- 실행하지 못한 검증과 그 이유
- 실제 관련 이슈·티켓
- 동작을 이해하는 데 필요한 스크린샷
- 호환성·마이그레이션·배포·복구 안내가 필요한 경우 그 내용

대화 이력·중간 시도·폐기한 접근은 최종 설계 판단에 필요할 때만 씁니다. 파일 변경 목록을 그대로 반복하거나 프로젝트와 관계없는 체크리스트를 붙이지 않습니다. 테스트·CI 성공은 확인한 것만 기록합니다.

## 범위와 리뷰

한 PR은 하나의 목적을 갖도록 합니다. 큰 변경은 의미 있는 단위로 나누되, 문서·생성 파일 때문에 줄 수가 많다는 이유만으로 기계적으로 나누지 않습니다. 최종 범위가 바뀌면 제목과 본문도 함께 고칩니다.

공개 설명에는 비밀값·개인 경로·내부망 주소·개인정보를 넣지 않습니다. 머지·배포는 별도 요청과 프로젝트 정책을 따릅니다.

기본 양식은 [PR 템플릿](../.github/pull_request_template.md), 검토 기준은 [코드 리뷰](code-review.md)에 있습니다. GitHub 템플릿은 입력을 돕는 양식이며 제목이나 규칙을 자동 강제하지 않습니다.
